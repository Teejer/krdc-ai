## 2. Fixed AI key combinations (Ctrl+A etc.) — three scancode bugs

The assistant's shortcuts arrived at the remote as bare key presses. Found by
logging every injected key and its RDP scancode (`QT_LOGGING_RULES="KRDC.debug=true"`).

1. **Generic modifier VKs don't exist in winpr's tables.** `VK_CONTROL` (0x11),
   `VK_SHIFT` (0x10), `VK_MENU` (0x12) convert to scancode **0** and vanish.
   Manual typing works because XKB resolves physical keys to the *specific*
   VKs (`VK_LCONTROL` 0xA2 …). Fix: inject left-side specific VKs everywhere.
   (Symptom in the log: `No scancode for virtual key 17 keyboard type 4`.)
2. **Enhanced keys need the KBDEXT tag** before conversion: Delete, arrows,
   Home/End, PgUp/PgDn, Insert, main Enter, right Ctrl/Alt, PrintScreen, Apps,
   volume/media. Without the tag winpr finds `VK_DECIMAL` at 0x53 instead of
   `VK_DELETE` and returns scancode 0.
3. **Special sequences the converter can't express**, sent directly instead:
   Win keys need `KBD_FLAGS_EXTENDED1` (E1 prefix), NumLock is E0 45,
   Pause is the 6-byte physical sequence.
4. `backtab` was silently a plain Tab — now expands to Shift+Tab.

## 3. The `hotkey` tool (string chords)

- llama.cpp-style backends drop **array** tool arguments (no `items` schema /
  unreliable parsers), so `press_key`'s `modifiers` array never arrived and the
  model fell back to one keystroke at a time.
- New `hotkey` tool: one string, modifiers first — `"ctrl+a"`, `"win+e"`,
  `"ctrl+shift+esc"`. `press_key` also accepts `"ctrl+a"` in its `key` field.
- Chord sender: all keys down together, final key tapped, held keys released on
  a 15 ms stagger via `QPointer`-guarded timers (no stuck modifiers, safe if
  the tab closes mid-chord).
- `AiKeys::qtKey()` learned `ctrl`/`control`/`alt`/`shift`/`option`/`opt`
  (it only knew `meta`/`win`/`super` — combos with other modifiers were
  "unknown key" errors) and `lwin`/`rwin`.
- Dangerous chords (Ctrl+Alt+Del, Win+L, Alt+F4, …) stay gated.

## 5. Fixed misclicks — coordinate mapping

**Root cause:** the model sees a *downscaled* screenshot (1432×794 → 1280×710)
but its coordinates were injected as raw screen pixels; the old prompt asked
the model to rescale them itself. Clicks landed short of target by the
downscale factor (~12%), worse far from origin.

- `AiConversation` remembers the exact image size it sent and maps
  move/click/drag/scroll from screenshot-pixels → screen-pixels itself.
- `take_screenshot` reports image size *and* screen size; `screen_info`
  returns both; prompt says the tools map for the model.
- Config: raised `ImageMaxSize` to 1600 and `ImageQuality` to 90 in krdcrc
  (screen now goes 1:1, no downscale).

## Reference: RDP scancode facts learned today

- Winpr VK→scancode tables contain only *specific* key VKs (L/R Ctrl, Shift,
  Alt); generic aliases (VK_CONTROL etc.) convert to 0.
- Enhanced keys are only found when the VK carries `KBDEXT` (0x100).
- Win keys need EXTENDED1; the winpr converter can never emit it.
- Pause = E1 1D 45 E1 9D C5 (no separate release); NumLock = E0 45.
- krdc manual path is fine — it converts XKB native scan codes, which resolve
  to the right VKs with the right extension bits automatically.
